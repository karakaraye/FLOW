# FlowPilot AI operations — Task 6B

These are reviewable examples, not a deployment. All five live provider verifications remain outstanding. Do not activate payments, email, messaging or AI based on fixture results.

## Architecture and boundaries

Use separate long-lived web and worker processes and PostgreSQL 17. PostgreSQL is the durable queue; browser lifetime is irrelevant. HTTPS terminates at a trusted edge. Only the edge publishes ports; never publish PostgreSQL or the worker. `deploy/compose.production.example.yaml`, `deploy/Caddyfile.example` and `deploy/database-roles.example.sql` describe this topology. Supply reviewed immutable image digests, a domain, trusted database CA/certificate, independent credentials and persistent volumes before any rollout. The outbound bridge is NOT an egress firewall: enforce provider allowlists in host/network infrastructure as well as the application SSRF controls. Do not use the local test adapter in production.

`FLOWPILOT_ENV=production` activates startup validation in both processes. NODE_ENV alone is insufficient because local verification uses production Next builds. The production example sets the flag explicitly. Missing/unsafe settings prevent startup. Public signup is disabled and login requires verified email: verified-email delivery and password-recovery delivery have not been provisioned, so public SaaS launch remains blocked. Do not manually mark arbitrary users verified to bypass this requirement.

Trust exactly one controlled proxy path. The edge overwrites X-FlowPilot-Client-IP with its peer address; auth refuses production writes without a valid address. Restrict direct access to web containers. If an upstream CDN is added, configure and verify its exact trusted ranges before interpreting forwarded client addresses. Never trust an arbitrary browser-supplied forwarded header.

## Configuration inventory

`.env.example` inventories development settings and operational additions. DATABASE_URL is a least-privilege runtime URL; DIRECT_DATABASE_URL is a separate direct/session-compatible migration connection. Production database URLs require sslmode=verify-full; configure the trusted CA. DB_POOL_MAX defaults to 5 per process. Budget replicas × pool maximum plus migrations/backups/admin headroom below database max_connections (example 100). Do not run migrations through transaction-mode pooling.

BETTER_AUTH_URL must be the canonical HTTPS origin. BETTER_AUTH_SECRET, vault keyring/active key, OPERATIONS_TOKEN, provider secrets, database credentials and BACKUP_ENCRYPTION_KEY belong in a server secret store, never NEXT_PUBLIC variables, image layers, Git, log collectors or client bundles. OPS token grants aggregate operational visibility only; protect and rotate it separately from auth. Keep web and worker vault/auth keys consistent. Each worker uses a separate heartbeat identity. Container health metadata contains no customer payloads.

Build on a separate CI/build machine with monitored disk headroom, rather than sharing constrained storage/CPU with PostgreSQL or workers. Local repeated image builds exhausted this verification workspace until disposable build layers were reclaimed; the interrupted browser runs were repeated. Build with `docker build -t flowpilot:review .` using the managed environment's prescribed proxy/CA configuration when applicable. `tsx` is a production dependency because the dedicated worker runs TypeScript. Runtime image runs as node without build dependencies; migrations require a separately reviewed build-stage/tooling job (`npx prisma migrate deploy` with the direct DDL URL), not runtime schema mutation. Never bake real environment files into an image. The Compose files are examples and have not been brought up against production infrastructure.

## Deployment and rollback procedure

1. Review source, lockfile, dependency audit, schema changes and this task's validation. Build and scan an immutable image. Test the same image in an isolated staging environment with integrations disabled.
2. Capture and verify an encrypted backup; record migration and image identifiers. Validate pool budgets, disk, CA trust, proxy routing, secrets and operator access. `npm run ops:check` reports only safe issue codes.
3. Pause admission and stop workers gracefully before incompatible migrations. Run `npx prisma migrate status`, then `npx prisma migrate deploy` once under the migration identity. No development reset, db push, automatic down migration or startup migration loop.
4. Start workers and web; verify readiness, worker heartbeat, metrics, login and tenant rejection. Run a synthetic internal workflow. Only then change traffic after separate approval.
5. Roll back application image only when the current schema remains compatible. Otherwise stop writes, preserve evidence and restore into a NEW database using the procedure below, then approve a deliberate connection cutover. Never reverse a destructive migration blindly. Keep expand/contract migrations and old images available.

## Backup and disaster recovery

Target RPO: 24 hours with daily encrypted dumps; target RTO: 4 hours. These are proposed objectives, not measured service guarantees. The small local restore drill does not demonstrate production-scale RTO. For tighter RPO, configure managed PostgreSQL WAL/PITR and independently test it. No backup scheduler, remote retention service or PITR has been activated here.

Use a dedicated SELECT backup identity with appropriate sequence/schema access. Install matching PostgreSQL 17 clients. Set BACKUP_DATABASE_URL, BACKUP_OUTPUT (a NEW path in a protected directory), BACKUP_KEY_ID and a dedicated random 32-byte base64 BACKUP_ENCRYPTION_KEY through the secret manager, then `npm run ops:backup`. Native clients use environment-based credentials rather than command arguments. PG_TOOL_CONTAINER is a local-test fallback only. Archives use AES-256-GCM and an authenticated format/key identifier; the companion JSON contains ciphertext hash/format metadata. Keep both files, keys separately, restrictive access and an off-host encrypted copy. Alert on a missed daily backup, failed upload, age >26h or storage exhaustion. Suggested retention: 7 daily, 4 weekly, 12 monthly, subject to customer policy and law. Deleting the only key makes backups unrecoverable.

Quarterly, and before risky migrations, restore into a NEW isolated database named `flowpilot_restore_*`. Set RESTORE_DATABASE_URL, RESTORE_CONFIRM_DATABASE to that exact name, BACKUP_INPUT and the matching encryption key; run `npm run ops:restore`. Restore refuses nonempty targets, wrong confirmation, the application's database name, tampered archives and invalid keys. It authenticates the archive before a single-transaction pg_restore. It never drops/cleans an existing database. Restrict concurrent database users/creators during recovery; advisory locking coordinates this tool, not arbitrary outside SQL. Temporary plaintext exists only in a private temporary directory and is removed on normal/failure completion; use encrypted scratch storage for production recovery and handle host crashes through secure cleanup.

Validate migration history, table constraints, tenant counts, credential decryption with retained vault keys and queued-job recovery in an outbound-isolated environment. Do not replay production provider side effects during a drill. Record start/end, archive checksum/key ID, results, actual RPO/RTO and responsible operator. Approve any traffic cutover separately. Application vault/auth keys must also be recoverable; the dump encryption key does not replace them.

## Worker failure and recovery

Allow SIGTERM grace of at least 180 seconds. Workers stop claiming, finish current bounded work and record STOPPED. Health checks require a fresh IDLE/BUSY record (<45s). Alert when no healthy worker exists for 60s with queued work, oldest queued age >5m, stale RUNNING lease >90s or failures rise. Inspect aggregate metrics and safe run IDs, never dump encrypted/raw inputs.

Queued work is durable. Database locks/transactions and leases prevent duplicate admission/claims; stale claims recover after lease expiry. Restart a failed worker after fixing connectivity/credentials. Pure computation can resume/retry safely. External effects may be UNKNOWN after a crash: do not blindly retry Gmail, WhatsApp, payments, HTTP or AI; inspect the existing idempotency/reconciliation state and provider evidence first. No exactly-once external-delivery guarantee is claimed. Never manually clear effect markers or leases to force a send.

## Monitoring, logging and incidents

GET /api/health/live is process liveness; GET /api/health/ready checks database and, in explicit production mode, a fresh worker and safe runtime. Readiness is not a complete provider check. GET /api/operations/metrics requires the dedicated Bearer OPERATIONS_TOKEN even for app owners. Metrics aggregate queue/run outcomes, worker counts, integration states, billing events and AI usage; they expose no tenant identity or payload. AI reservation totals represent recorded reservations, not a cash balance. Scrape over protected HTTPS every 30s. Alert on sustained 5xx >1%, auth/rate spikes, queue backlog, failed backup, stale worker, billing failures, AI UNKNOWN outcomes and database connection/disk saturation. Configure thresholds/baselines in your actual monitor; no external monitor is installed.

Request IDs are regenerated at the boundary, never trusted from clients. Structured logs permit only fixed event/code, IDs, route class, duration/status/count and safe worker metadata. No raw exception messages, URLs/query strings, request/response bodies, tokens or email addresses are intentionally logged. Edge access logging is disabled in the example to avoid webhook/query secrets. Configure collector access and retention (suggested 14 days), encryption and redaction separately. Framework/database/platform logs require independent review; application allowlisting is not a universal DLP guarantee. Operational aggregates expire after 72h and old heartbeat rows after 7 days via worker maintenance.

Incident procedure: restrict access/disable the affected integration, preserve safe correlation IDs and encrypted evidence, revoke compromised sessions and provider tokens, rotate the affected secret, assess tenant impact, reconcile uncertain external actions, communicate through approved incident channels, restore service and document cause/action. Do not paste credentials into tickets. For a suspected cross-tenant defect, pause admission and isolate affected reads before investigating. Changing auth secret invalidates sessions and may affect encrypted queued payloads: drain/cancel safely and preserve required old recovery keys first.

## Rotation, retention and privacy

Rotate DB/operator/provider credentials independently using overlap and verified cutover where supported. For vault rotation, introduce a new active key while retaining old read keys, use existing integration/webhook rotation operations with tenant authorization, and verify decryptions before retirement. Billing, AI results, WhatsApp events and pending OAuth state also use encrypted fields: a complete all-purpose bulk re-encryption tool is NOT provided; retain old keys until all such data and backups expire or a separately reviewed migration rewrites them. Never remove an old key merely because new writes succeed. Meta recipient HMAC identities require their stable hash key; blind rotation can break identity matching. Provider revocation is separate from deleting local ciphertext.

Review existing workflow/event retention and provider-specific cleanup before launch. Do not log contact/message/AI content. Customer deletion requires verified authorization, disabling ingress and integrations, stopping queued work, revoking provider grants, deleting tenant data in foreign-key-safe order and auditing completion without content. No complete self-service account erasure/export flow is delivered by this task. Define legal retention for billing/audit records and backup expiry; restored backups can resurrect deleted data, so replay deletion tombstones before reconnecting traffic. Never promise instant deletion from immutable backups.
